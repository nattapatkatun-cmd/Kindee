# Kindee — Calculation & Data-Consistency Audit
**Date:** 2026-07-25 · **Scope:** `index.html` (12,394 lines), `worker/worker.js` (215 lines)
**Status:** audit findings below are as-found at commit `ee07414`. Most HIGH/MED items were fixed in `c68bdaa` — see §L for what was fixed, what was deliberately left, and what changed behaviour.

**Method:** read-only source audit across 6 parallel domain passes. Every finding is traced to actual code and reproduced with a worked numeric example. Nothing here is inferred from behaviour — all line references were read directly. No files were modified.

**Legend:** 🔴 HIGH = a number the user can see contradicts another number the user can see, or drives a wrong health recommendation · 🟠 MED = wrong/misleading in a reachable case · 🟡 LOW = cosmetic, dead code, or physiologically thin

## 0. Executive summary

| # | Theme | Sev | Core issue |
|---|---|---|---|
| **A** | Activity double-count | 🔴 | `netCal = intake − burn − NEAT` is charted against a goal of `BMR × 1.55 − deficit`, which already contains that burn and that NEAT. ~590–680 kcal/day of phantom deficit. |
| **B** | Two "Net Cal" definitions | 🔴 | Weight tab uses **raw** workout burn; Fitness tab uses **credited** burn. Same day, 200 kcal apart, both plotted against the same goal line. |
| **C** | Sleep-score placeholders | 🔴 | `stages` and `physio` fall back to a hard-coded 50 at full 20 % weight each. 40 % of a phone-only user's score is a constant — and entering a *bad* RHR scores worse than leaving it blank. |
| **D** | Dead quality gates | 🔴 | The duplicate-log "Data Error" gate is mathematically unreachable; `inconsistent` is read before assignment; the 25 %-of-TDEE deficit re-cap is a no-op above TDEE 2400 — while the UI claims it fired. |

## A. 🔴 Activity is counted twice

**Where:** `7315-7321`, `7432-7437`, `7508-7516`, `9056-9077`, `4416-4421`, `5367-5381`

`getDailyMetrics` returns `netCal = intake − creditedWorkoutBurn − neatCal` (`5381`). The calorie goal is `TDEE − deficit` where `TDEE = BMR × activityMultiplier` (`5124`), default **1.55** = "moderate exercise 3–5×/week" (`5119`) — which already contains both the workout and the walking.

The comment at `5350-5358` justifies the 0.50/0.60/0.80 burn credit *only* on the grounds that MET is gross energy. It never addresses the activity-multiplier overlap. That is the hole.

The **dashboard is correct** (`4656-4663`: gross intake is primary, with the comment *"Adaptive TDEE รวม workout+NEAT ไว้แล้ว"*). Three other places do the forbidden comparison:

1. **Fitness "Net Calories" chart** (`7453-7520`) plots net bars *and* a dashed goal line at `S.goals.cal`, colours bars green when `v <= goalCal` (`7433`), and the tooltip reads `' Net Cal: ' + y + ' (' + (y - goalCal) + ' จากเป้า)'` (`7514`).
2. **`renderWeightCalChart`** (`9056-9087`) — same bars, same colours, same goal reference.
3. **Anomaly flag 3** (`4404-4421`) — the comment says *"Deficit/surplus must be judged against TDEE"* and correctly switches the **reference** from goal to TDEE, but keeps `net = intake − burn − neat` (`4418`). Half the fix.

**Worked example** — 35 y male, 70 kg, 175 cm, activity 1.55, recomp:
BMR (Mifflin, `5115`) = 1624 → TDEE = **2517** → goal = 2517 − 250 = **2267**.
Day: intake 2200 · 45-min strength logged 400 kcal, user-typed → `cal_source:'override'` → credit 0.50 → 200 · 12,000 steps, `session_steps` blank → NEAT = 480.
`netCal` = 2200 − 200 − 480 = **1520**.

| Surface | Shows | Truth |
|---|---|---|
| Dashboard | "เหลือกินได้ 67 kcal" | ✅ correct (2267 − 2200) |
| Fitness net chart tooltip | "Net Cal: 1520 kcal (**−747** จากเป้า)", green bar | ❌ overstated by **680 kcal** |
| Same chart, intake tooltip | "Intake: 2200 (−67 จากเป้า)" | ✅ — *both tooltips are on the same chart* |

680 kcal/day ≈ 4,760/week ≈ **0.62 kg/week of fat loss that does not exist**.
Cross-check from the expenditure side: 1.55 already grants `1624 × (1.55 − 1.2)` = **568 kcal/day** of activity. Subtracting 680 more counts ~1,248 kcal of activity on a day whose true above-resting activity is ~660 kcal (~348 net workout + ~312 net steps) → **~590 kcal/day genuinely double-counted**.

**Fix direction:** either compare net against `BMR × 1.2`, or (simpler, and what the dashboard already does) compare **gross intake vs goal everywhere** and remove the goal line from the net charts.

### A2. 🔴 The two Net Cal charts disagree with each other
`7317` uses `creditedBurnSum(...)`; `9058` uses raw `a + w.calories_burned`. Every other net computation in the file is credited (`4416`, `4583`, `5379`, `9970`) — `9058` is the lone exception.
Same scenario day: **Fitness tab = 1520, Weight tab = 1320.** 200 kcal apart, both against the same `goalCal`.

### A3. 🟠 `calcStepCalories` uses a gross constant as a net deduction
`7018-7022`: `steps × 0.04 × (weight/70)`. The constant is used consistently (only two occurrences: `7021` and the UI label at `1196`) — the issue is physiological, not a contradiction. 0.04 kcal/step at 70 kg is a fair **gross** figure; **net** (above resting) is ≈0.026. 12,000 steps → app 480, net truth ≈312 → **+168 kcal/day** before the A1 double-count.

### A4. 🟠 `session_steps` de-dup is manual-only; `isStepBased` is dead
Four presets carry `isStepBased:true` (`6723-6726`, stored at `6819-6820`) — the flag is **never read anywhere else in the file**. No auto-fill, no warning. The input is labelled *ไม่บังคับ* (`1113-1116`) and defaults to 0.
45-min road run, MET 8.5, 70 kg → `calcBurnKcal` 446, credited 0.80 = 357; the ~6,000 steps it generated also land in NEAT = 240. **597 kcal subtracted for one 446-kcal-gross session** — on top of A1.

### A5. 🟡 MET constant is ~4.8 % low, and that mislabels honest users
`6828`: `met × weight × (minutes/60)` — the standard is `MET × 3.5 × kg / 200 × min` = `× 1.05`. 45 min / 8.5 MET / 70 kg → standard 469, app 446.
Side effect: `cal_source` detection uses `Math.abs(diff) <= 1` (`6935-6936`), so a user who types the *textbook-correct* 469 is tagged `'override'` and credited **0.50** instead of 0.80.

### A6. 🟡 Other
- **Pattern detector P4 unreachable** (`4596`): needs `net > goal + 200`, i.e. intake > 3147 on a 2267 goal for anyone who logs steps.
- **Weight source split** (`6827` `S.profile.weight` fallback **65** vs `7020` `getLatestCheckinWeight()` fallback **70**): an unconfigured user is 65 kg for workouts and 70 kg for steps simultaneously.
- **Water goal** (`7087-7089`): `clamp(weight × 35, 1500, 4000)`. Used consistently (dashboard `7127`, AI prompt `3849`), so no contradiction — but no activity/sweat term, in a Thai-climate app where a 45-min session adds 500–1000 ml.

## B. 🔴 Dead quality gates — written correctly, unreachable as shipped

### B1. The duplicate-log "Data Error" gate can never fire
```js
9945:  var rawLogRate = calDays.length / Math.max(daySpan, 1);
9947:  var dataError  = rawLogRate > 1.05;   // ">105% = likely duplicate logs"
```
`calDays` comes from `getDateRangeMetrics(cutoffStr, todayStr)` (`9921`) keyed by date (`9929`). That helper emits **exactly one row per calendar date** (`5383-5391`), and `daySpan` (`9908`) is that same count. So `calDays.length ≤ daySpan` **always** → `rawLogRate ≤ 1.0` → `dataError` is **permanently false**, and the `Math.min(rawLogRate, 1.0)` cap on `9946` is a no-op.

The irony is documented in the file: the comment at `9926-9931` explains that the `if (!m.meals.length) return` filter was *added* to fix logRate always reading ~100 %. That filter is precisely what made the gate unreachable.

**Dead as a result:** `statusLabel='Data Error 🔴'` (`10206`), the red suppression banner (`10330-10333`), `confBase = min(confBase, 40)` (`10254`), `intakeReliability ≤ 30` (`10266`), the AI's `- Data Error:` line (`10555`) and RULE 2 (`10567`).

*Scenario:* user double-logs every meal for 14 days → `calDays.length = 15`, `daySpan = 15` → rawLogRate 1.00. Card shows "100 % log", Confidence ~92 %, AI is told "Data Error: NO", and Adaptive TDEE is computed from doubled intake — the exact case the gate exists for.

### B2. `inconsistent` is read before it is assigned
```js
10155:  if(actualDeficit!==null && !likelyWaterNoise && !inconsistent && !dataError){
10156:    currentPace7d = ... ;
...
10175:  var inconsistent=false;          // ← declared 20 lines later
```
`var` hoisting makes `inconsistent` `undefined` at `10155`, so `!inconsistent` is **always true**. The comment at `10152-10153` promises suppression "where the deficit signal is unreliable (water noise / conflict / error)" — the conflict path is dead. `likelyWaterNoise` has the same ordering problem: it is still mutated afterwards at `10189`, `10194`, `10198`.

*Scenario:* 70 kg, trend **+0.40 kg/wk**, avgIntake 1900, trueTDEE 2500 → actualDeficit 600 → `inconsistent = true` (`10179-10182`). The card renders the red **"⚠️ Inconsistent Data Detected"** banner *and*, in the same view, `pace ปัจจุบัน (จาก deficit จริง 600 kcal/วัน): −0.55 กก./wk` (`10427`) directly above `TREND CONTEXT: Scale +0.40 กก./wk` (`10431`). The AI is told both (`10556`, `10566`).

### B3. The 25 %-of-TDEE safety re-cap is a no-op above TDEE 2400 — and the UI claims it fired
```js
5159:  var targetDeficit = Math.max(200, Math.min(600, feasG.requiredDeficit));   // already ≤600
5166:  var safeCap = Math.round(baseTDEE * 0.25);
5167:  deficit = (status==='aggressive'||status==='unrealistic') ? Math.min(targetDeficit, safeCap) : targetDeficit;
```
`safeCap < 600` only when `baseTDEE < 2400`. Above that the `Math.min` does nothing — yet `updateGoalModeHint` (`5343`) *unconditionally* prints **"(ปรับลดจาก target-timeline เพราะเกินเกณฑ์ปลอดภัย)"** whenever the status is flagged.

*Scenario:* male 75 kg / 175 cm / 30 y / 1.55 → TDEE **2633**, 25 % = **658**. Target 22 %→15 % BF over 12 wk; at week 6 with %BF unmoved, `calcTargetFeasibility` shrinks the duration (`7602-7605`) → `requiredDeficit = 1132`, `pctBW = 1.37 %/wk` → `'unrealistic'`. Result: `min(600, 658) = **600**` — identical to uncapped. The guardrail is inert exactly for the higher-TDEE users whose 25 % line sits furthest from 600.

### B4. 🟠 Confidence bonus reads a field that never exists
`10259` reads `visualAnalysis.confidence`; the Gemini schema (`9806`) defines `confidenceScore`, and the renderer reads `r.confidenceScore` (`9836`). The `+5` is dead — InBody + photo users sit 5 points below intent.

## C. 🔴 Sleep score — placeholders at full weight

### C1. The comment says missing pillars are dropped; two are forced to 50
```js
10680:  // Never-measured pillars stay null and get dropped via re-normalization below.
10685:  if (stages === null) stages = 50;
10687:  if (physio === null) physio = 50;
```
Only `efficiency` and `consistency` ever reach the `.filter(p => p.v != null)` on `10695`. `stages` and `physio` keep their full **0.20 weight each** → **40 % of every phone-only user's score is a constant 50**. `buildResultHTML` (`10819`) then renders `Sleep Stages 50` / `HRV / Physio 50` as measured bars, with no "no data" marker — unlike Efficiency/Consistency, which *are* conditionally hidden on the same line.

*Scenario* — bed 23:40, wake 06:20 recorded as 4.0 h, no TIB/stages/HRV, first night (`consistency = null`):
duration 15 (.25) + stages 50 (.20) + physio 50 (.20); wSum 0.65 → `(3.75+10+10)/0.65 = 36.5 → **37**` → label **"Fair"**, headline *"การนอนโดยรวมอยู่ในระดับปานกลาง"* (`10709`) — **for a 4-hour night.** Every night under 6 h reads "Fair" for this user, permanently.

### C2. Entering an honest bad measurement scores worse than leaving it blank
The no-data placeholder is 50; real bad data scores 32–40 (`10662-10676`).

*Scenario* — bed 23:40, wake 06:20, hours 6.67, TIB 6.83, deep 60 min, REM 90 min, **RHR 78**, consistency null:
duration 45 · efficiency 95 · stages 100 · physio **35** → wSum 0.85 → **67** → Good / **Moderate 🟡**.
Same night, RHR box left **empty** → physio 50 → **71** → Good / **Optimal 🟢**.
Crossing `total >= 70` (`10699`) flips recovery status, emoji, and the AI's Push prior — which drives a **+150 kcal / +30 g carb** goal change (`3665-3667`). *Deleting one true field buys a green badge and 150 calories.*

### C3. Accepting a "Rest" recommendation on a rest day **raises** calories 200 kcal
`getEffectiveGoalToday()` = `getRecoveryAdjGoals() || getDayTypeAdjGoal() || S.goals` (`4303`) — the two adjusters are mutually exclusive, and `getRecoveryAdjGoals` rebuilds from **raw `S.goals`** (`4160`), discarding the rest-day cut entirely.

*Scenario* — baseline 2000 kcal / 200 g carbs, planned rest day, no workout logged:
- Before: `getDayTypeAdjGoal()` → **1800 kcal / 150 g carbs**, dashboard shows the rest-day note (`4649-4652`).
- Recovery returns `Rest` → `delta 0, carbDelta −20, proDelta +15`, reason *"คงแคลเท่าเดิม"* (`3672`). User taps ใช้เป้าหมายนี้.
- After: **2000 kcal / 180 g carbs** — **+200 kcal and +30 g carbs versus the target that was already on screen**, and the rest-day note vanishes (the object carries `_adj`, not `_dayType`).

The **Push** branch is explicitly guarded against this collision (`restDayPlan`, `3661-3664`). The **Rest** branch is not.

### C4. 🟠 Recovery adjustment breaks macro↔calorie reconciliation
- Push (`3666`): `delta 150` but `carbDelta 30` = **+120 kcal** → 30 kcal orphaned.
- Rest (`3671`): `delta 0`, `−20 g carb + 15 g protein` = **−20 kcal**, against an unchanged calorie target. The code comment calls it *"(≈isocaloric)"* — a true isocaloric swap of −20 g carb is **+20 g** protein, not +15.

The app's own validator `updateMacroKcalHint` (`5458-5465`) flags any gap > 15 kcal in **red**. Both branches exceed it: **the app generates a daily goal that its own Settings screen would mark as an error.**

### C5. 🟠 Three definitions of "how much sleep you need", all on one card
| Source | Value |
|---|---|
| `computeSleepNeedHours` (`11351-11361`) | median of your own last 60 d, floored at 7 |
| `computeGradualBedtimeTarget` call sites (`10733`, `3573`) | hard-coded **8** (`goalHours \|\| 8` at `11226` is never exercised) |
| `buildWeakPillarAction` (`11406`) | hard-coded string *"เพื่อให้ถึง 8 ชม."* |
| `scoreDuration` (`10627-10635`) | 7–7.99 h = **72**; peak 95 only at 9–9.5 h |

*User sleeping 7.2 h consistently* sees, on one screen: no debt badge (need = 7.2 → debt ≈ 0), a bedtime target 48 min earlier (wake − 8 h), the tip "get to 8 hours", a Duration bar of **72/100**, and the AI told "need **7.2** h/คืน" (`3584`). Four numbers, one card.

### C6. 🟠 Other sleep issues
- **Efficiency can exceed 100 %** (`10636-10643`, no upper guard) and lands in the top band. A screenshot import misreading TIB prints *"หลับจริง 107 % ของเวลาบนเตียง"* (`11409`) and *"Sleep Efficiency: 107 % (optimal)"* into the AI prompt (`3553`). Nothing asserts `hours <= timeInBed`; `saveSleep` validates only `1 ≤ hours ≤ 14`.
- **Oversleeping outranks a solid night** (`10627-10635`): 8.0–8.99 h → 88, but >9.5 h → **90**. A 12-hour night beats 8.5 h. Everything 1.0–5.99 h returns a flat 15 — a 2 h and a 5.9 h night are indistinguishable.
- **The deterministic score is gated behind an AI call.** `saveSleep` (`10895-10934`) never calls `calculateSleepScoreFromData`; `sleepScore` is written **only** at `3630` inside the Gemini `.then`. Nights logged without running the AI are blank in the trend chart (`11494`) and excluded from behaviour correlations (`11589`), so `buildBehaviorSleepTip` needs ~10 *AI-analyzed* nights, not 10 logged nights. The score is 100 % deterministic and could be computed at save time.
- **AI prompt's Physio rubric is 0-25 while every other pillar is 0-100** (`3593` vs `3595`): 25/20/14/8 are `scorePhysio`'s 100/80/56/32 pre-multiplied by 0.25, and the prompt then says to multiply by 0.20 again. The app discards the AI's number (`10716-10720`) so the score is safe — but `detail`/`strengths`/`improvements` are AI free text and **are rendered** (`10821-10823`) next to a green `HRV / Physio 100` bar.
- **Screenshot import** (`10980-10994`): asks for `<int|null>` but never validates; `sleepHours: 7.5` → `parseInt` → **7**, 30 min gone silently. Fields are **not cleared** on a missing value (`10983`, `10990`) — import B without stages shows *"ไม่พบ: Deep Sleep"* while the field still holds import A's 60 min, and that stale value is what saves.
- **Sheet import** (`9332-9344`) pushes rows whole — no whitelist, no range check, no `consistency` recompute, no 120-day trim (unlike `syncSleepLog`, `11465-11467`). The chart plots that raw `sleepScore` while the card *recomputes* it (`10716`); the two can disagree for imported nights.

## D. 🔴 Meal data is never reconciled

### D1. No macro↔calorie check exists on the meal path
The identity `P×4 + C×4 + F×9` appears at exactly **6 lines** in the file — `3217`, `5192`, `5195`, `5199`, `5458`, `10510` — all of them goal-engine or display-hint code. **None is on the meal path.**
- `saveMeal` (`3128-3155`) stores the AI's `calories/protein/carbs/fat` verbatim.
- `confirmManual` (`3183-3208`) saves the typed `cal` even when it contradicts the typed macros; `3217` computes the implied kcal but writes it only to a text hint — it never blocks or corrects.

A meal saved as `650 kcal, P20 C30 F15` (macros imply 335 kcal) makes the calorie ring and the macro rings tell two different stories about the same food — and every downstream number (`netCal` `5381`, avgIntake → Adaptive TDEE, weekly review, AI prompts) inherits the calorie figure while the macro rings inherit the other.

### D2. `showResult` reconciles calories to item sums but not macros — in the same 8 lines
```js
3074:  r.calories = (aiCal > 0 && Math.abs(aiCal - sumCal) < sumCal * 0.1) ? aiCal : sumCal;   // 10% tolerance
3075:  r.protein  = +r.protein  || sumPro;                                                     // no check at all
```
*Scenario:* 3 items, AI total 900 kcal vs item sum 1200 (>10 % off) → calories corrected to **1200**. AI total protein 40 g vs item sum 62 g → protein stays **40**.
The meal-breakdown UI prints each item's P/C/F (`3099`), so the user sees items summing to 62 g under a header that says 40 g. `showResult` mutates `curResult`, so this persists into `saveMeal`.

## E. 🟠 Competing values for "the goal" and "the rate"

### E1. TDEE source flips day to day with no user action
`readAnalyzerContext` (`5126-5142`) returns the cached `gd_calorie_context` **only if `ctx.date === today`**; otherwise it falls back to `window._wtAnalysisData`, which is in-memory and lost on reload → returns `null` the next day. Then `getOfficialCalorieContext` (`5209`) resolves `adaptiveTDEE || formulaTDEE || settingsGoal || 1800`.

Day the analysis ran: officialTDEE = adaptive (e.g. 2250) → `modeGoal.cal` 1800.
Next morning, fresh load: officialTDEE = **formula** (e.g. 2480) → `modeGoal.cal` **2030**, while the dashboard ring still reads 1800 from `S.goals`.
`formatCalorieContextLine` (`5282`) already prints both when they differ — the author saw this — but the Settings hint and the AI prompts still consume `officialGoal`.

### E2. Same-day analysis cache survives a new weigh-in and a goal change
`gd_wt_analysis` is cleared at `9439`, `9531`, `9601`, `9730` (body-comp / progress-photo edits) but **not** by `handleSaveWeight` (`9187`), `handleDeleteWeight` (`9247`), `applyGoalValues` (`5285`), `saveGoals`, `calcGoal`, or `syncRecommendedCalToGoal`.

*Scenario:* goal 1800. Morning → analysis caches `recommendedIntake 1800`, `requiredDeficit 600`. Afternoon → sync button sets `S.goals.cal = 2150`. Re-pressing วิเคราะห์ hits the same-day cache (`9861`) and still shows "Intake ที่แนะนำ: **1800**", "Deficit ที่ต้องการ: 600", next to a sync button offering 2150. `_wtAnalysisData` is restored from cache (`9864-9867`) so **the AI Deep Dive is told "Calorie goal the user set: 1800"** (`10542`) while Settings reads 2150.

### E3. Two different "recommended intake" from one analysis run
`saveAnalyzerCalorieContext` (`5306-5312`) stores `d.centralGoal.cal` as both `goalCal` and `recommendedIntake`. But the analyzer overwrites its own `recommendedIntake` twice afterwards without updating `centralGoal`:
```js
10133:  if (trueTDEE != null) recommendedIntake = Math.round(trueTDEE - recompDeficit);
10134:  engineRecommendedIntake = recommendedIntake;
```
*Scenario (recomp hold):* trueTDEE 2400, mode `fat_loss` (preset deficit 450), weight target met, falling fast → `recompDeficit = 0` → card prints "รักษา ~**2400** kcal maintenance" (`10405`) and the sync button offers 2400 (`10475`). Meanwhile `centralGoalForAnalysis.cal = 1950` → `gd_calorie_context.recommendedIntake = 1950` → the daily-summary prompt is told "Goal Engine Recommendation: **1950**" (`3820`). **450 kcal apart, same minute.**
Line `10134` also replaces a floored value with an **unfloored** one, bypassing the 1500 M / 1200 F floor (`5151`).

### E4. `syncRecommendedCalToGoal` writes a goal that fails the app's own validator
```js
10508:  goal.cal = Math.round(cal);                                              // bypasses the gender floor
10510:  goal.crb = Math.max(80, Math.round((goal.cal - pro*4 - fat*9) / 4));     // floor kept, compensation dropped
```
`buildGoalFromMode` ends with `fat` reduction (`5195`) **and** `cal = max(cal, macroSum)` (`5199`) precisely because the 80 g carb floor can exceed the target. Both steps are missing here.
*Scenario:* 60 kg female, `fat_loss` (pro 120 g = 480, fat 48 g = 432), sync 1100 → `crb = max(80, 47) = 80` (320) → saved goal **1100 kcal with macros summing to 1232**. `updateMacroKcalHint` then shows *"รวมจากมาโคร ≈ 1232 kcal · เกินเป้าแคลอรี่ 132 kcal"* on the screen the sync just wrote.

### E5. `buildGoalFromMode` inflates `cal` past TDEE−deficit; the hint still says TDEE−deficit
`5199` silently raises the target when floors bind, but `updateGoalModeHint` (`5341`) still prints `"TDEE {tdee} - {deficit} kcal"`.
*Example:* TDEE 2000, target-derived deficit 600, 100 kg male 35 %BF → hint says **1400**, calorie box shows **1574**. 174 kcal, unexplained.

### E6. Protein basis: mislabeled, and discontinuous at the %BF threshold
`5184-5189`: `proLBM = lbm × (proteinPerKg + 0.4)`; `highBF` = ≥25 % M / ≥32 % F. `proteinBasis = 'lbm'` is set in **both** branches (`5189`).
- **Mislabel:** at 20 %BF male fat_loss, `proLBM = 0.80w × 2.4 = 1.92w < proBW = 2.0w`, so the BW basis wins — but the hint (`5344`) prints *"Protein 2.4g/kg Lean Mass"*.
- **Discontinuity:** 24.9 %BF → 2.0w; 25.0 %BF → `0.75w × 2.4 = 1.8w`. **The protein target drops 0.2 g/kg (13 g at 65 kg) as body fat goes up by 0.1 point.**

### E7. `gd_daily_summary` not invalidated by recovery-apply or plan-save
Cleared in 10 places, but **not** by `applyRecoveryAdj` (`4183-4195`), `cancelRecoveryAdj` (`4196-4205`), or plan save (`8608`). Apply a +150 recovery adj after generating the summary and the ring shows the new goal while the cached AI Daily Coach still quotes the old one.

### E8. Recovery/rest-day goal not used where it is compared against
`getEffectiveGoalToday()` is used at `3699`, `4035`, `4645`, `5626`, `7172`, `12104` — but `renderCorrelations` uses `S.goals.cal` (`4566`), `renderWeeklyReview` uses it (`4458`), and the fitness chart's goal line uses it (`7324`). On a confirmed Push day the dashboard targets 2150 while the correlation panel and the chart's goal line still say 2000.

## F. 🟠 Fitness Target / body composition

### F1. %BF rate mixes measurement sources; the anchor is InBody-only
`currBF` is **InBody-only by explicit design** (`7757-7761`, with a comment saying so). But `getBFTrajectory`'s slope (`7810`) regresses over **every source mixed together** — no filter. The per-source outlier detector (`9382-9405`) deliberately avoids cross-source comparison; this function does not.

The *label* is fixed; the prescription is a nutrition-policy call — should protein keep rising with body weight at high %BF, or track lean mass? Two clean options: always use `max(BW, LBM)` (never drops), or always use LBM (smooth but lower for lean users).

### Behaviour changes worth knowing
